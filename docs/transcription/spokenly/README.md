## Automatic Activation Semantics

Spokenly's Automatic activation mode gives one shortcut two behaviors:

| Interaction with Right Option | Result |
| --- | --- |
| Brief press and release | Toggle recording on or off |
| Press and hold | Start push-to-talk; releasing the key stops recording |

This is different from the current Wispr Flow profile. Wispr uses Right Option
for hands-free toggle and Fn for push-to-talk, so its two behaviors require two
different application shortcuts.

The installed Spokenly binary describes Automatic mode as holding the shortcut
while speaking for push-to-talk or pressing it briefly to toggle recording.
The live `Default Mode` preference independently confirms
`activationMode: "automatic"`.

Spokenly's official Modes documentation also lists Automatic, Toggle,
Push-to-talk, and Double-tap as supported activation styles:

- [Spokenly Modes documentation](https://spokenly.app/docs/modes)

## Live Preference Representation

The current profile is stored in `modes.v2` inside:

```text
~/Library/Preferences/app.spokenly.plist
```

`modes.v2` is JSON stored as plist data. Its shortcut-relevant shape is:

```json
{
  "name": "Default Mode",
  "id": "00000000-0000-4000-8000-000000000001",
  "modeMac": "autoInsert",
  "shortcut": {
    "id": "00000000-0000-4000-8000-000000000001",
    "activationMode": "automatic",
    "trigger": {
      "keys": {
        "_0": {
          "rawFlags": 64
        }
      }
    }
  }
}
```

`rawFlags: 64` is Spokenly's serialized representation for the configured
Right Option trigger in this live profile. Prefer Spokenly's settings UI when
changing it instead of treating this private encoding as a stable public API.

Rebuild or reinstall the tracked helper with:

```text

```

The helper is a background-only application and does not appear in the Dock.
It changes no Spokenly preference. Its only action is to open the official
`spokenly://toggle` URL.

The former global F20-to-Right-Option BTT adapter
`1F6581F7-5158-4562-96BC-4651E63C893D` was removed after physical tests showed
that Logitech-generated F20 did not enter BTT's keyboard-trigger pipeline.
Another test used a modified middle-click plus BTT's high-level mouse-event
mode; BTT did not capture that event either. Direct BTT action tests produced
synthetic modifier events that Spokenly ignored. The later `Ctrl+Shift+B` BTT
adapter also failed because the thumb-button event never reached BTT. None of
these failed routes is part of the live setup. The current adapter avoids both
keyboard emulation and synthetic modifiers.

## Collision With Wispr Flow

Both providers currently listen for Right Option:

| Provider | Right Option behavior |
| --- | --- |
| Spokenly | Automatic: tap toggles, hold enables push-to-talk |
| Wispr Flow | Hands-free toggle only |

Running both providers at the same time can still cause physical Right Option
inputs to collide. The three device deeplink adapters are Spokenly-specific,
but the initial switcher should still enforce one active provider rather than
merely launching another app.

## `trx` Provider Switch

The implemented switcher uses process exclusivity and redirects all three
physical device inputs between providers.

```text
trx spokenly
trx wispr
trx toggle
trx status
trx verify
```

Selecting Spokenly:

1. Snapshots the current BTT triggers, Logitech database, provider state, and
   application state.
2. Changes the trackpad and Magic Mouse BTT actions to launch
   `Spokenly Toggle.app`.
3. Changes the MX Master `c195` assignment in every current Logitech profile
   to the `Spokenly Hands-Free` Smart Action.
4. Verifies all three mappings and both Logitech databases.
5. Stops Wispr Flow, launches Spokenly by bundle ID `app.spokenly`, and verifies
   the application state.
6. Records `spokenly` in `~/Library/Application Support/trx/active-provider`.

`trx wispr` performs the reverse, restoring Right Option for both BTT triggers
and every Logitech profile before starting Wispr Flow. On failure,
`trx` attempts to restore every snapshotted component. Backups live under
`~/Library/Application Support/trx/backups/` and operational logs live at
`~/Library/Logs/trx.log`.

The switch does not modify either application's shortcut preferences. It only
changes the BTT and Logitech device adapters plus application process state.

## Fast Activation Options

The terminal command is implemented. Other launch surfaces remain optional.

| Activation option | Experience | Trade-off |
| --- | --- | --- |
| Terminal command | Run `trx toggle`, `trx spokenly`, or `trx wispr` | Implemented and easiest to debug |
| One BTT keyboard shortcut | Cycle the provider and show a notification | Fast globally, but consumes another global shortcut |
| Raycast script command | Select a named provider from Raycast | Discoverable, but depends on Raycast being available |
| Shell picker | Choose a provider and invoke `trx` | Scales well as more providers are added, but takes more keystrokes |

Only add a BTT or Raycast launcher after deciding which physical shortcut
should own that activation.

## Stronger Future Dispatcher

Process exclusivity solves provider collisions but does not make synthetic
Right Option events acceptable to Spokenly. A later hardware-level dispatcher
could preserve key duration if push-to-talk is ever required.

Conceptually:

| Selected provider | Short input | Held input |
| --- | --- | --- |
| Spokenly | Send a Right Option tap | Hold Right Option until physical release |
| Wispr Flow | Send a Right Option tap | Hold Fn until physical release |

This would provide one consistent logical input across providers with different
shortcut models. It requires a hold-capable physical signal. The current
trackpad 3-finger tap and Magic Mouse TipTap are discrete gestures, so they
cannot communicate duration without being replaced or supplemented by a
press-lifecycle gesture.

Do not implement this dispatcher until the desired push-to-talk gestures for
the trackpad and Magic Mouse are chosen.

## Spokenly Automation Hooks

Spokenly exposes official deeplinks that may help later automation:

| Action | Deeplink |
| --- | --- |
| Start main mode | `spokenly://start` |
| Stop recording | `spokenly://stop` |
| Toggle recording | `spokenly://toggle` |
| Start a mode | `spokenly://start?mode_id=<id>` |
| Toggle a mode | `spokenly://toggle?mode_id=<id>` |
| Switch mode without recording | `spokenly://switch?mode_id=<id>` |
| Open keyboard controls | `spokenly://tab/shortcuts` |

Source: [Spokenly deeplink documentation](https://spokenly.app/docs/macos/deeplinks).

These deeplinks control recording and modes. The MX Master adapter now uses the
documented toggle deeplink. The URL handler was resolved to the installed
Spokenly application without activating recording. Deeplinks do not select
Spokenly over another global transcription provider, so the provider switcher
still needs process exclusivity or an event dispatcher.

## Verification Checklist

1. Run `trx spokenly`, then run `trx verify`.
2. Confirm Spokenly is running and Wispr Flow is stopped with `trx status`.
3. Briefly press physical Right Option and verify toggle recording.
4. Hold physical Right Option, speak, and release to verify push-to-talk.
5. Test the trackpad 3-finger tap as a toggle.
6. Test the MX Master auxiliary/thumb button as a toggle.
7. Test Magic Mouse TipTap Left as a toggle.
8. Confirm browser middle click, Back, and Forward remain unaffected.
